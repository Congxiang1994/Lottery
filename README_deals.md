# 捡漏（Deals）· 实现文档

> 2026-10-28 需求定稿并上线。一句话：自动盯「什么值得买」好价流，只留下
> **值友认可度高**的条目，省掉每天刷首页的时间；点卡片直接去原站下单页。
> 全站定位见 [README.md](./README.md)。

## 1. 背景与目标

用户是「什么值得买」重度用户，核心诉求是**捡漏**，但现状是每天要花时间刷首页
判断哪些值得买一件。目标：把「值不值」的判断交给规则，人只看结果。

判据不是「评论多」，而是「值友投票认可」—— 详见 §4。

## 2. 已确认的决策

| 项 | 决策 |
|---|---|
| 数据源 | **只抓 PC 站好价列表页** `/p2/`…`/pN/`；**不抓详情页**（理由见 §3） |
| 排除的通道 | `m.smzdm.com`（202 全量挑战）、任何带 `?` 的接口（robots 明确 `Disallow: /*?*`） |
| 抓取节奏 | 每 20 分钟一轮、每轮 5 页；日请求量约 360 次，远低于实测安全线 |
| 限速 | 进程内令牌桶，请求间强制 ≥3 秒；命中验证码即**退避 30 分钟** |
| 多 worker | 文件 flock（非阻塞）抢本轮执行权，抢不到就跳过；持有者崩溃内核自动释放 |
| 登录凭据 | 存**会话 Cookie**，不存账号密码（SMZDM 登录有滑块，脚本密码登录走不通） |
| 凭据录入 | 管理页粘贴 `Copy as cURL` 整条命令，后端解析出 `Cookie` + `User-Agent`；也接受裸 Cookie 串 / 单行 `Cookie:` 头 |
| 凭据展示 | 永不回显原文，只给脱敏串（`sess=ABC…998877（共 52 字符）`）；落库于 `smzdm.db`（0600/0700） |
| 入选判定 | 关注分类 + 值率硬门槛 + 值/收藏/评论三选 N（见 §4），全部可在管理页配置 |
| 关注分类的语义 | **只影响「入选/展示」，不影响入库**；非关注品类照常入库，改配置后历史立即可用 |
| 改阈值生效 | 保存时后台自动重算全库，公开页立即变化，不用等下一轮抓取 |
| 未入选数据 | 一并入库（`picked=0`），公开页 SQL 层硬过滤，只有管理页能看全量 |
| 历史保留 | 好价 30 天、抓取日志 14 天，每轮结束顺手清理 |

## 3. 为什么只抓列表页

实测（2026-10-28）`/p2/` 的每张卡片里就已经带齐了全部判据：

| 字段 | 解析锚点 |
|---|---|
| 值 | `icon-zhi-o-thin"></i><span>N</span>` |
| 不值 | `icon-buzhi-o-thin"></i><span>N</span>` |
| 收藏 | `title="收藏数 N"` |
| 评论 | `title="评论数 N"` |
| 价格 / 商城 | `z-highlight` 容器文本 / `'mall_name':'…'` |
| 分类 | `'1级分类':'…'` `'2级分类':'…'` |
| 卡片标签 | `feed-block-tags` 内的 `<i>`（如「34天新低」「比上次发布低42%」） |
| 缩略图 | `z-feed-img` 内的 `img[src]` |
| 上架时分 | `feed-block-extras` 内的 `HH:MM` |

详情页（单条 300KB~1MB）只有正文，**没有任何额外的价格历史或「历史低价」标记**
（实测搜索 `历史低价/绝对值/价格走势` 均 0 命中）。

结论：一页列表 ≈ 18 条有效好价的完整判据，一次请求；抓详情要 18 次请求、十几 MB。
这个取舍是整个方案能把请求量压到日 360 次的根本原因。

### 3.1 一个必须注意的坑：文章卡与好价卡同 id

同一篇内容在列表里会渲染**两张卡**：一张文章卡（无 `channel`、无 `price-btn-up`）、
一张好价卡（`channel=youhui`、有值按钮），**两者 id 相同**。

所以解析顺序必须是「**先按 `channel=youhui` 剔非好价卡，再做 id 去重**」。
反过来做的话，文章卡先入表、真好价被 `id in seen` 挤掉，症状很隐蔽：
标题对，但价格和商城是空的。

## 4. 入选判定

```
值率 = 值 / (值 + 不值) × 100
门槛：属于关注分类  且  值率 ≥ worth_pct_min  且  打分样本 ≥ 5
命中：值 ≥ worth_min、收藏 ≥ fav_min、评论 ≥ cmt_min 三项中满足 ≥ need_hits 项
```

默认值：值率 85%、值 100、收藏 300、评论 100、`need_hits=2`、
关注分类 `电脑数码,手机通讯,数码配件`、每轮 5 页。

**分类名的层级要知道**（2026-10-28 实测 `/fenlei/`）：`电脑数码`、`家用电器` 是顶部
导航里的**一级分类**；`手机通讯`（slug `shouji`）、`数码配件`（slug `shumapeijian`）是
`电脑数码` 块内的**二级分类**（`<h3>` 分组）。也就是说手机本就被 `电脑数码` 覆盖，
显式列出只是防站点改层级。`in_cate()` 同时匹配 `cate1` 与 `cate2`，多写不产生成本。

**为什么值率是硬门槛而不是"三选一"之一**：SMZDM 上评论数高经常是因为大家在吵
（价格争议、发货翻车），「被喷」同样会推高评论数。值率是真人投票的直接结果，
先过关才谈热度。

**为什么样本量 <5 直接否**：「1 个值 0 个不值」= 100% 值率，但样本量毫无意义。

**分类判定在 `judge()` 里做，不在入库前做**（2026-10-28 修正）：

初版在 `scheduler.run_round()` 里先按分类过滤再入库，结果是**非关注品类一条都不进库**。
三个后果全都会踩：① `cate_stats()`（职责就是「告诉你实际分布在哪些品类」）只能看到
关注品类，等于自废；② 用户改关注分类后历史数据为 0，得重新攒满保留期才发现漏；
③ 请求量由 `pages` 决定，分类过滤本来就省不了请求，节流是伪收益。
现在改为**全量入库**，分类只参与 `picked` 判定 —— 公开页 SQL 层按 `picked=1` 硬过滤，
管理页仍能看全量分布。

综合热度 `heat = 值×1.0 + 收藏×1.2 + 评论×1.5`，**只影响列表排序，不参与判定**。

## 5. API

### 5.1 公开（无鉴权）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/deals/list` | 入选好价列表。参数 `limit / offset / cate / q / hours`。SQL 层硬过滤 `picked=1` |
| GET | `/api/deals/stats` | 顶部摘要：今日新增 / 今日命中 / 累计 / 最近一轮 |

### 5.2 管理（`deals_session` cookie，复用全站操作密码）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/deals/admin/auth` | 密码校验 → 签发 12h httpOnly cookie |
| GET | `/api/deals/admin/session` | 会话是否有效 |
| POST | `/api/deals/admin/logout` | 退出 |
| GET | `/api/deals/admin/config` | 读配置（`cookie` 恒为空串，另给 `cookie_masked`） |
| PUT | `/api/deals/admin/config` | 写配置；含阈值字段时自动 `rejudge` 全库并回传 `picked/changed` |
| DELETE | `/api/deals/admin/cookie` | 清除已存 Cookie |
| GET | `/api/deals/admin/status` | 调度健康 + 统计 + 最近轮次 + 近 72h 分类分布 |
| POST | `/api/deals/admin/fetch` | 手动触发一轮（异步，结果看 status） |
| POST | `/api/deals/admin/unban` | 手动解除风控退避 |
| GET | `/api/deals/admin/preview` | 含未入选的全量数据（调阈值时看效果） |

## 6. 前端

| 路径 | 页面 | 说明 |
|---|---|---|
| `/deals` | 公开页 | 双列信息流；时间范围筛选（24h/3天/7天/全部）；卡片点击新标签打开原站 |
| `/deals-admin` | 管理页 🔒 | 运行状态 / 入选阈值 / 登录 Cookie / 关注分类；单页滚动，不分 Tab |

入口登记三处（新增产品必改）：`Portal.tsx` 的 `APPS`、`App.tsx` 路由、
`Nav.tsx` 的 `useNavLinks`。

**空态设计**：判定门槛是爆款级，列表空是常态而不是故障。所以空态必须展示
「最近一轮抓了多少条 / 命中几条」，否则用户无法区分「没抓到」和「抓到了但都不够格」。

**分类名未命中要显式报警**：配了 `cate_filter` 却一条都没命中时，
`fetch_log.errors` 会写入实际出现的分类名 —— 分类名是站点侧定义的，会变。

## 7. 运维

```bash
# 库位置（与其它域同目录，权限 0600/0700）
/data/lottery/smzdm.db

# 看抓取健康
curl -s 'https://doudoutech.cloud/api/deals/stats'

# 看最近轮次（需管理会话）
#   浏览器登录 /deals-admin → 运行状态区块
```

**新增列迁移**：`store.init()` 内有 `_ensure_columns()`，按 `PRAGMA table_info`
补列。`CREATE TABLE IF NOT EXISTS` 对已存在的表不会加列，升级时漏了这步会在
第一次 INSERT 时报 `no such column`。

**风控表现与处置**：

| 现象 | 含义 | 处置 |
|---|---|---|
| `fetch_log.banned=1`、errors 含「反爬页」 | 命中腾讯防水墙 | 自动退避 30 分钟；换 IP 或过完验证码后可点「解除」 |
| `last_result.notes` 含「没有关注分类的条目」 | **正常**：该品类本轮确实没供给（数码仅占 ~1.4%） | 无需处理；看 `parsed`/`added` 确认抓取本身是通的 |
| errors 含「近 7 天从未出现过」 | 关注分类名真的失效了（站点改名/调层级） | 看管理页分类分布 chips，按实际名称改。样本 <400 条时不会报，避免新库误伤 |
| 连续多轮 `parsed=0` 且无报错 | 页面结构变了 | 检查 `crawler.py` 里的解析锚点 |

**为什么「没命中关注分类」不再进 errors**：数码类供给只占 1.4%，每轮几乎必然 0 命中。
把它当错误会让状态栏每轮标红，用户会误判功能坏了 —— 所以它降级为 `notes`（提示不告警），
`errors` 只留给真问题。`ok` 字段因此恢复「只在真出错时为 false」的语义。

**合规**：只抓纯路径 URL（robots 的 `Disallow: /*?*` 已排除所有带查询串的地址）；
不转载正文，只保留标题、价格摘要与跳转链接；低频个人使用。

## 8. 已知限制

1. **发现延迟**：最长 20 分钟（轮询间隔）。要更快只能缩短间隔，但请求量线性上升。
2. **秒杀类抓不到**：库存消失极快的好价，20 分钟内可能已售罄。
3. **品类供给极不均衡**：实测好价流里「电脑数码」只占 **1.4%**（两轮样本合计 73 条
   里 1 条），食品生鲜约 40%、日用百货约 36%。所以关注数码时「整天没结果」是正常
   供给现象，不是抓取故障 —— 管理页的分类分布 chips 就是用来区分这两种情况的。
   想提高命中率只有三条路：放宽阈值、加页数（管理页 1~5）、把关注分类扩到
   **「家用电器」**（真正的一级新品类；`手机通讯`/`数码配件` 本就属于 `电脑数码`，
   加进来不增加供给）。
4. **Cookie 会过期**：失效后表现为「反爬页」或跳登录页，需在管理页重粘一次。
5. **没有历史价格**：站点页面不提供价格走势，所以无法判断「是否真的历史低价」，
   只能依赖卡片标签（如「34天新低」）与值友投票。
6. **分类页不可用**：`/fenlei/diannaoshuma/` 虽可访问（HTTP 200）且 robots 未禁，
   但卡片是 Vue 组件 `haojia-card-container` 渲染，**没有收藏数与评论数**，
   无法满足判定需求，故放弃「按品类频道定向抓取」这条更优路线。
