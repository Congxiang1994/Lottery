# 捡漏（Deals）· 实现文档

> 2026-10-28 需求定稿并上线；2026-10-29 第二轮改造（**抓标签流 + 折扣优先判定**）。
> 一句话：自动盯「什么值得买」的**手慢无 / 绝对值 / 历史低价 / 多重优惠叠加** 四个标签流，
> 按**折扣深度**排序 —— 不看投票数，只看「折得狠不狠」；点卡片直接去原站下单页。
> 全站定位见 [README.md](./README.md)。

## 1. 背景与目标

用户是「什么值得买」重度用户，核心诉求是**捡漏**，但现状是每天要花时间刷首页
判断哪些值得买一件。目标：把「值不值」的判断交给规则，人只看结果。

第一版用「值友投票认可」当判据（值率 + 值/收藏/评论三选二），上线后用户反馈
**「捞到的都是正常的好价，感觉一般般」** —— 这是判据本身的问题，不是阈值没调好：

- 值 / 收藏 / 评论都是**被曝光之后**才产生的。刚发布 10 分钟的真漏无人投票，
  永远进不来；能攒 500 值的必是人人认识的大牌常规促销（iPhone 打折）。
- 改造前生产库：619 条入库，仅 14 条入选（2.3%），全是「值 5~12、靠评论勉强过线」。

**折扣率是唯一与曝光无关的客观信号**：正文里「活动售价 505 元…到手 254.41 元」
就是 5.0 折，不管有没有人投过票。第二轮改成折扣优先，实测立刻捞出
骆驼登山鞋 2.0 折（值仅 2）、米家扫地机 3.3 折 1307 元（值 6）、海尔冰箱 3.9 折 987 元（值 0）。

## 2. 已确认的决策

| 项 | 决策 |
|---|---|
| 数据源 | **主力：4 个标签流**（手慢无 `tz273gm` / 绝对值 `t8joxpm` / 历史低价 `t8602je` / 多重优惠叠加 `toor6ly`）× 每流 2 页；**兜底：首页推荐流 `/` 1 页**；**补充：`/top/` 排行榜每 3 轮一次**（只取「电脑数码」tab）。精选流 `/jingxuan/pN/` 代码保留但**默认 0 页**（实测是全量爆料流水，见 §3.0）；**不抓详情页**（理由见 §3.2） |
| 排除的通道 | `m.smzdm.com`（202 全量挑战）、任何带 `?` 的接口（robots 明确 `Disallow: /*?*`）；`/fenlei/{slug}/youhui/`（301 回退导购聚合页）、`/baoliao/`（是提交表单不是列表）、`/tag/{中文名}/`（301，**必须直接存 slug**） |
| 抓取节奏 | 每 10 分钟一轮、每轮 10 次请求（4 标签 × 2 页 + 首页 1 + 排行榜平均 1/3）；日请求约 1440 次（平均 1 次/分钟），仍在实测安全线内 |
| 限速 | 进程内令牌桶，请求间强制 ≥3 秒；命中验证码即**退避 30 分钟** |
| 多 worker | 文件 flock（非阻塞）抢本轮执行权，抢不到就跳过；持有者崩溃内核自动释放 |
| 登录凭据 | 存**会话 Cookie**，不存账号密码（SMZDM 登录有滑块，脚本密码登录走不通）。**管理页已移除入口**（2026-10-29）：好价流匿名可读，配了反而有异地登录风险；后端保留字段作逃生通道，用本地脚本 `get_smzdm_cookie.py --push` 注入 |
| 入选判定 | 黑名单否决 + **三档折扣判定**（≤50% 直接入选 / 50~70% 需热度 1 项 / >70% 或无折扣退回旧判据），全部可在管理页配置（见 §4） |
| 关注品类的语义 | **只影响排序加权，完全不影响入选**。排序键是 `discount / (cate_hit ? cate_boost : 1)` —— 所以列表**不是裸折扣单调**，2.9 折的数码排在 2.0 折的运动户外之前是设计结果 |
| 改阈值生效 | 保存时后台自动重算全库（含 `cate_hit`），公开页立即变化，不用等下一轮抓取 |
| 未入选数据 | 一并入库（`picked=0`），公开页 SQL 层硬过滤，只有管理页能看全量 |
| 历史保留 | 好价 7 天、抓取日志 14 天，每轮结束顺手清理（7 天对齐前端筛选档；若把精选流打开，日入库会涨到几千条、30 天攒成十几万行，把「保存阈值时的全库重算」拖到秒级） |

## 3. 抓哪些入口（一天试了 7 个，最后落在标签流）

### 3.0 七入口实测：标签流才是真漏的来源

2026-10-29 一天里把入口试了个遍，过程值得留着 —— 因为结论推翻了第一版。

**同一时刻抓 102 条样本**（每个入口 20 条左右）：

| 入口 | 排序 | 值中位 | 收藏中位 | 过旧阈值 | 数码占比 |
|---|---|---|---|---|---|
| `/`（首页推荐流） | 算法推荐序 | 2 | 10 | **0/18** | 0% |
| `/jingxuan/pN/`（精选流） | 时间序 | 0 | 0 | 0/20 | 35% |
| `/tag/tz273gm/`（手慢无） | 时间序 | 12 | 27 | **4/20 (20%)** | 0% |
| `/tag/t8joxpm/`（绝对值） | 时间序 | 16 | 134 | **4/20 (20%)** | 15% |
| `/tag/t8602je/`（历史低价） | 时间序 | 4 | 10 | 2/20 (10%) | 0% |
| `/tag/toor6ly/`（多重优惠叠加） | 时间序 | 2 | 3 | 1/20 (5%) | 10% |
| `/top/`（榜单） | — | — | — | 无值按钮 | — |

**结论 1：标签流是唯一稳产真漏的入口。** 手慢无 20% 过线率、绝对值 20%，
而首页推荐流 0/18 —— 第一版盯的恰恰是唯一不产出的那个。

**结论 2：值友投票是「曝光」的结果，不是「时间」的函数。**
精选流每分钟新增 6.7 条（≈9600 条/天），是全量爆料流水 —— 大量用户随手发的爆料，
根本没人看。实测抓 p1（0 分钟）、p5（10 分钟）、p10（30 分钟）、p20（2.3 小时）、
p40（7.5 小时）各 20 条，**热度并不随时间上升**（值中位数始终 0~1，收藏 0~1）。
所以「用时间序换低延迟」这条路不通：能进库，但永远不入选。

**结论 3：但标签流也不该靠投票筛。** 标签流里 20% 能过旧阈值，这 20% 是
「值 12、收藏 27 的老牌促销」；真正值 0~6 的折扣好货（3.9 折冰箱、3.3 折扫地机）
仍然进不来。**换入口只能拿到「稍好一点的样本」，判据不改就永远停在这个水平。**

### 3.0.1 折扣率从哪来

好价正文摘要里有原价，正则抽出来即可（`discount_of()`）：

```
活动售价 505 元，下单立减 100 元，到手 254.41 元  →  原价 505 / 到手 254 → 5.0 折 = 50
```

- 只接受 1~100% 的结果（原价 ≤ 到手价视为抽错，记 0 = 未知）
- 可提取率约 **46%**，其中一半落在 5 折以内
- 抽不到就退回旧判据（不因为「没折扣」直接否决，否则会漏掉真正的历史低价）

### 3.1 顺带修掉的两个浪费

**① 首页分页早已失效。** `/p2/`…`/p7/` 返回的基本是同一屏，与首页重叠 13/18
（只多 5 条，带不带 cookie 都一样）。现在首页只抓 1 页，主力交给标签流翻页
（标签流是时间序，p2 真的是上一批，不重叠）。

**② 频率翻倍反而更省。** 间隔从 20 分钟缩到 10 分钟，每轮 10 次请求 → 日 1440 次，
平均 1 次/分钟，仍在安全线内（3 秒令牌桶让单轮约 28 秒跑完）。

> ⚠️ 两个延迟别混：「**发布 → 进库**」≤10 分钟（标签流是时间序，这里是真正的
> 低延迟入口）；「**进库 → 被大量值友看到**」不由我们决定。
> 第一版说的「发布 → 被推荐 181 分钟」只适用于首页推荐流。

精选流的代码与开关留着（`pages_per_round` 0~8，默认 0）：真要做「刚上新」这类
功能时它是现成的数据源，但**不要拿它当入选来源**。

### 3.2 卡片里已带齐全部判据

实测各入口的卡片 HTML 都含全部判据（2026-10-28 首次确认，2026-10-29 在精选流复核 20/20、
标签流复核 4/4）：

| 字段 | 解析锚点 |
|---|---|
| 值 | `icon-zhi-o-thin"></i><span>N</span>` |
| 不值 | `icon-buzhi-o-thin"></i><span>N</span>` |
| 收藏 | `title="收藏数 N"` |
| 评论 | `title="评论数 N"` |
| 价格 / 商城 | `z-highlight` 文本 / `'mall_name':'…'` |
| **原价（算折扣用）** | 正文摘要里的 `原价` / `售价` / `市场价`（见 §3.0.1） |
| **爆料人** | 卡片底部的用户昵称（标签流专有，首页/精选流约半数没有） |
| 分类 | ⚠️ 首页 `'1级分类'`、精选流 `'cate_level1'`（**两套键名都要认**） |
| 卡片标签 | `feed-block-tags` 内的 `<i>`（如「34天新低」「比上次发布低42%」） |
| 站点分类标签 | 卡片内的 `/fenlei/` 链接（与营销标签不是一回事，见 `clean_tags()`） |
| 缩略图 | `z-feed-img` 内的 `img[src]` |
| 上架时分 | `feed-block-extras` 内的 `HH:MM`（精选流 19/20 命中，首页约 4/18） |

详情页（单条 300KB~1MB）只有正文，**没有任何额外的价格历史或「历史低价」标记**
（实测搜索 `历史低价/绝对值/价格走势` 均 0 命中）。

结论：一页列表 ≈ 18~20 条有效好价的完整判据，一次请求；抓详情要 20 次请求、十几 MB。
这个取舍是整个方案能把请求量压到日 144 次的根本原因。

### 3.3 三个必须注意的解析坑

**坑 1：标签流必须按 `data-article-id="` 切分卡片。** 该属性写在 `class` **之前**，
按 `class="list list_preferential"` 切会让每张卡捡到**下一张卡**的 id，于是投票数
全部匹配到邻居 —— 症状是「所有卡的值/收藏/评论都是 0」，**不报错、不进日志**。
首页与精选流按 `class` 切没问题，标签流不行。

**坑 2：文章卡与好价卡同 id。** 同一篇内容在列表里会渲染两张卡：文章卡（无 `channel`、
无 `price-btn-up`）与好价卡（`channel=youhui`、有值按钮），**两者 id 相同**。
所以顺序必须是「先按 `channel=youhui` 剔非好价卡，再做 id 去重」。反过来做的话，
文章卡先入表、真好价被 `id in seen` 挤掉，症状很隐蔽：标题对，但价格和商城是空的。

**坑 3：价格容器结构不同。** 首页是 `<div class="z-highlight"><a>8.45元</a></div>`，
精选流是 `<a class="z-highlight">99元</a>`（自己就是带 class 的元素）。
只认「div + 内部 a」的写法，精选流的价格会全部解析成空 —— 不报错、不入错误日志，
只是卡片上一片空白。2026-10-29 实测 59/77 条空价格才发现。

**附带：标签会被分页导航污染。** 正则 `href="[^"]*/tag/[^"]*"` 会把底部的
`<a href="/tag/tz273gm/p2/">2</a>`、`下一页` 一起抓进来，标签变成
「手慢无|拼单|上一页|1|2|3|4|5|6|下一页」。统一过 `clean_tags()`：剔纯数字、
上下页、以及非中文的内部代号（`hjxy` / `yszb3` / `raw_struct` / `AIcheck_union`）。

## 4. 入选判定

```
① 一级/二级分类命中黑名单（cate_blacklist）        → 否决，连阈值都不看
② 有折扣数据（正文里抽到了原价）：
     折扣 ≤ discount_direct (50)                   → 直接入选，不看投票
     discount_direct < 折扣 ≤ discount_assist (70) → 热度三项命中 need_hits 项即可
     折扣 > 70                                     → 落到 ③（折得不够狠）
   新人价护栏：折扣 < 10 且到手价 < 5 元           → 否决（首购礼金/新人补贴，限购 1 件）
③ 无折扣数据 → 旧判据：
     值率 = 值/(值+不值)×100 ≥ worth_pct_min 且打分样本 ≥ 5
     且 值 ≥ worth_min、收藏 ≥ fav_min、评论 ≥ cmt_min 三项中满足 ≥ need_hits 项

排序： (discount > 0) DESC,
       discount / (命中关注品类 ? cate_boost : 1.0) ASC,
       heat DESC, first_seen DESC
```

默认值：`discount_direct=50`、`discount_assist=70`、`newbie_discount=10`、`newbie_price=5`、
值率 85%、值 50、收藏 50、评论 20、`need_hits=1`、黑名单 `金融服务`、`cate_boost=1.6`、
标签流 4 个 × 2 页、首页 1 页、精选流 0 页。

`discount_mode=0` 可一键回滚到纯旧判据（管理页开关），用于对比效果或应急。

### 4.1 旧阈值的天花板（为什么必须换判据）

2026-10-29 拿线上 517 条实际数据做网格搜索。原默认 100 / 300 / 100 是按「爆款」
想象的，比实际分布高一个数量级 —— 收藏 p90 只有 49，评论 p90 只 18：

| 组合（值率/值/收藏/评论，三选二） | 17.8h 入选 | 折合每天 |
|---|---|---|
| 85 / 100 / 300 / 100（原默认） | 7 | 约 6 |
| **85 / 50 / 50 / 20（第一版默认）** | **20** | **约 16** |
| 85 / 30 / 30 / 10 | 26 | 约 21 |

值率 85% 一直不是瓶颈（样本 ≥5 的条目里有 57 条能过），过严的从来是那三个绝对数。
但**上限就是「约 16 条/天的大牌常规促销」** —— 阈值怎么调都突破不了，因为它在筛曝光量。
第二轮换判据后：同一批 169 条入库、**74 条入选（50 条带折扣）**，入选率 2.3% → 44%，
且榜首是真的 2~4 折。旧阈值现在只做「无折扣时的兜底」。

### 4.2 为什么关注品类改成「加权」而不是「过滤」

实测「电脑数码」在好价流里只占 **0.6%**（517 条样本里 3 条）。硬过滤下：

- 每天最多 1 条，17.8 小时实测就是 1 条（用户原话「只有 1 条入选」）；
- 把门槛降到零也只有 1~1.4 条/天 —— **这不是调阈值能解决的问题，是供给结构问题**。

改成加权后：全品类都参与判定，命中关注品类的在排序键上除以 `cate_boost`（默认 1.6）
往前排（不漏数码），列表里还会带「关注」标记。第二轮实测标签流里「家用电器」占比明显
高于首页（扫地机、冰箱、净水器都能进榜），加权仍保留 —— 换来的是「同折扣下数码先出」。

> ⚠️ 别再写「`heat × cate_boost`」：那是第一版排序。现在是折扣排序键**除以** boost，
> 所以在页面上看到「2.9 折排在 2.0 折前面」是**正确行为**，不是排序坏了
> （2.9/1.6=1.81 < 2.0/1=2.0）。写 UI 断言时必须用这个键，别拿裸折扣比单调。

**分类名的层级要知道**（2026-10-28 实测 `/fenlei/`）：`电脑数码`、`家用电器` 是顶部
导航里的**一级分类**；`手机通讯`（slug `shouji`）、`数码配件`（slug `shumapeijian`）是
`电脑数码` 块内的**二级分类**（`<h3>` 分组）。也就是说手机本就被 `电脑数码` 覆盖，
显式列出只是防站点改层级。`cate_hit()` 同时匹配 `cate1` 与 `cate2`，多写不产生成本。

### 4.3 黑名单为什么要有

好价流里混着「每日领京豆」「签到领红包」这类**不是商品**的帖子，`cate1` 是
「金融服务」，但热度可以很高（值 500、收藏 900）—— 它们会挤满捡漏榜单。
黑名单在判定最前面直接否决，连阈值都不看。

**为什么值率是硬门槛而不是"三选一"之一**：SMZDM 上评论数高经常是因为大家在吵
（价格争议、发货翻车），「被喷」同样会推高评论数。值率是真人投票的直接结果，
先过关才谈热度。

**为什么样本量 <5 直接否**：「1 个值 0 个不值」= 100% 值率，但样本量毫无意义。

**判定始终在 `judge()` 里、数据始终全量入库**（2026-10-28 修正，2026-10-29 保持）：

初版在 `scheduler.run_round()` 里先按分类过滤再入库，结果是**非关注品类一条都不进库**。
三个后果全都会踩：① `cate_stats()`（职责就是「告诉你实际分布在哪些品类」）只能看到
关注品类，等于自废；② 用户改关注品类后历史数据为 0，得重新攒满保留期才发现漏；
③ 请求量由 `pages` 决定，分类过滤本来就省不了请求，节流是伪收益。
现在**全量入库**，判定只看阈值与黑名单 —— 公开页 SQL 层按 `picked=1` 硬过滤，
管理页仍能看全量分布。

## 5. API

### 5.1 公开（无鉴权）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/deals/list` | 入选好价列表。参数 `limit / offset / cate / q / hours`。SQL 层硬过滤 `picked=1`，按 `(discount>0) DESC, discount/(关注品类?boost:1) ASC, heat DESC` 排序 |
| GET | `/api/deals/stats` | 顶部摘要：今日新增 / 今日命中 / 累计 / 最近一轮 / 当前阈值与加权系数（含 `discount_mode/direct/assist`） |

`/api/deals/list` 单条返回的关键字段（前端卡片直接用）：

| 字段 | 说明 |
|---|---|
| `discount` | 整数百分比，`33` = 3.3 折，`0` = 未抽到折扣 |
| `reporter` | 爆料人昵称（标签流专有，可能为空） |
| `feed_tags` | 站点分类归属，`|` 分隔（手慢无/绝对值/历史低价…） |
| `source` | `tag` / `home` / `jingxuan` / `top`，排查「这条从哪来」 |
| `pick_reason` | 入选原因（`3.3折`、`2.9折 · 关注品类`、`值120` 等，空 = 未入选） |
| `cate_hit` | 是否命中关注品类（排序加权用） |

| `/deals-admin` | 管理页 🔒 | 运行状态 / **折扣判定（开关 + 4 个阈值）** / **抓取来源（标签 chips 点选 + 页数 + 请求量估算）** / 热度阈值（无折扣时兜底） / 关注品类（含加权系数）/ 品类黑名单；单页滚动，不分 Tab |

入口登记三处（新增产品必改）：`Portal.tsx` 的 `APPS`、`App.tsx` 路由、
`Nav.tsx` 的 `useNavLinks`。

**空态设计**：列表空是常态而不是故障。所以空态必须展示「当前门槛具体是多少」
（从 `stats.thresholds` 取，不硬编码 —— 用户改完阈值后写死的文案会变成假话）
与「最近一轮抓了多少条 / 命中几条」，否则用户无法区分「没抓到」和「抓到了但都不够格」。
`discount_mode` 开/关时空态文案要分支 —— 开着却说「值率 ≥85%」同样是假话。

**品类名未命中要显式报警**：配了 `cate_filter` 却近 7 天一条都没命中（且样本 ≥400 条）时，
`fetch_log.errors` 会写入实际出现的品类名 —— 品类名是站点侧定义的，会变。

```bash
#   浏览器登录 /deals-admin → 运行状态区块
```

**新增列迁移**：`store.init()` 内有 `_ensure_columns()`，按 `PRAGMA table_info`
补列。`CREATE TABLE IF NOT EXISTS` 对已存在的表不会加列，升级时漏了这步会在
第一次 INSERT 时报 `no such column`。

> 🔴 **依赖新列的索引绝不能写进 `_SCHEMA`。** 2026-10-29 把
> `CREATE INDEX idx_deals_discount ON deals(discount)` 写进 `_SCHEMA`，旧库启动即崩：
> `CREATE TABLE IF NOT EXISTS` 不加列 → 建索引先于补列 → `no such column: discount`
> → lifespan 里 `init()` 抛异常 → gunicorn 起不来 → **全站 502**。
> 一律在 `init()` 里 `_ensure_columns()` **之后**单独建。
> ⚠️ 本地新建库测不出来（新库建表就带新列）—— 验迁移必须**伪造一个旧结构库**跑
> `init()`，并注入坏 schema 确认它在该库上真会抛错。

**风控表现与处置**：

| 现象 | 含义 | 处置 |
|---|---|---|
| `fetch_log.banned=1`、errors 含「反爬页」 | 命中腾讯防水墙 | 自动退避 30 分钟；换 IP 或过完验证码后可点「解除」 |
| `last_result.notes` 含「没有关注品类的条目」 | **正常**：该品类本轮确实没供给（数码仅占 ~0.6%），且它已不影响入选 | 无需处理；看 `parsed`/`added` 确认抓取本身是通的 |
| errors 含「近 7 天从未出现过」 | 关注品类名真的失效了（站点改名/调层级） | 看管理页品类分布 chips，按实际名称改。样本 <400 条时不会报，避免新库误伤 |
| 连续多轮 `parsed=0` 且无报错 | 页面结构变了 | 检查 `crawler.py` 里的解析锚点 |

**为什么「没命中关注品类」不进 errors**：数码类供给只占 0.6%，每轮几乎必然 0 命中。
把它当错误会让状态栏每轮标红，用户会误判功能坏了 —— 所以它降级为 `notes`（提示不告警），
`errors` 只留给真问题。`ok` 字段因此恢复「只在真出错时为 false」的语义。

**合规**：只抓纯路径 URL（robots 的 `Disallow: /*?*` 已排除所有带查询串的地址）；
不转载正文，只保留标题、价格摘要与跳转链接；低频个人使用。

## 8. 已知限制

1. **发现延迟现在只剩一段**：标签流是时间序，**发布 → 进库 ≤10 分钟**（轮询间隔，
   由我们决定）。第一版盯首页推荐流时还有「发布 → 被推荐 中位 181 分钟」那一段，
   现在不依赖推荐位了。代价是标签流里的条目投票少，所以判据必须靠折扣（§4）。
2. **秒杀类抓不到**：库存消失极快的好价，10 分钟内可能已售罄。
3. **折扣抽不到就没有折扣**：可提取率约 46%（另有 54% 的正文没写原价/或抽到异常值）。
   抽不到时退回旧判据，所以榜单里会混着少量「值达标但折数未知」的条目 ——
   它们的 `discount=0`，排序上全部沉到列表末尾，不影响榜首质量。
4. **品类的供给结构集中在食品日用**：首页推荐流里「电脑数码」占 **0.6%**（517 条样本里 3 条），
   食品生鲜约 37%、日用百货约 35%。标签流好一些（绝对值/多重优惠里数码约 10~15%），
   但仍然不是数码频道。本域的对策是不拿品类当门槛、只用排序加权 ——
   榜单里会有非数码商品，这是刻意的取舍。想更偏数码就把 `cate_boost` 调大（上限 5.0）。
5. **Cookie 会过期**（若配置过）：失效后表现为「反爬页」或跳登录页。管理页已无入口，
   用 `get_smzdm_cookie.py --push` 重新注入。
6. **没有历史价格曲线**：站点不提供价格走势接口，所以「是否真的历史低价」只能靠
   **正文里写的原价**（→ 折扣率）与卡片标签（「34天新低」），不能校验原价本身是否虚高。
7. **分类页不可用**：`/fenlei/diannaoshuma/` 虽可访问（HTTP 200）且 robots 未禁，
   但卡片是 Vue 组件 `haojia-card-container` 渲染，**没有收藏数与评论数**，
   无法满足判定需求，故放弃「按品类频道定向抓取」这条更优路线。
8. **改造前入库的老记录没有折扣**：`discount=0`、排在列表末尾，等它们再次出现在流里
   会被补上，或在 7 天保留期内自然过期（2026-10-29 上线时存量 589 条）。

## 9. 登录 Cookie（管理页已移除入口，仅留脚本通道）

> 2026-10-29 决策：**管理页不再有 Cookie 区块**。理由见本节末「要不要配」——
> 好价流匿名可读，配了收益不确定而代价落在你的账号上。后端 `cookie` / `cookie_ua`
> 字段与 `DELETE /admin/cookie` 保留，作为真被风控掐死时的逃生通道。
> 下面内容留档，需要时照着做。

**现象**：在 smzdm.com 按 F12，DevTools 会不停停在 `debugger` 上，Network 面板根本用不了。

**机制**（已实测确认，不是猜测）：首页会向 HTML 里注入一个随机路径的脚本
（形如 `/C2WF946J0/probev3.js`），内容是 `__TENCENT_CHAOS_VM` —— 腾讯的 JS 虚拟机混淆。
它自带一套字节码解释器，而 `debugger` 是它的**一个操作码**（`case 0: debugger`），
再由 `setInterval` 反复驱动 VM。于是只要有调试器附着，就会被无休止地断在 VM 内部。

**两条路**：

1. **不用 F12（首选）**：本机跑
   `python3 ~/.workbuddy/scripts/lottery-web/get_smzdm_cookie.py --push`
   * 直接读浏览器自己的 cookie 库（SQLite）并解密，再调管理接口写入。
   * 解密参数（已在本机 17/17 条验证）：macOS 口令取自 Keychain
     `Chrome Safe Storage`，`PBKDF2-HMAC-SHA1(salt="saltysalt", 1003 次, dkLen=16)`
     → AES-128-CBC，IV 为 16 个空格，密文带 `v10` 前缀；
     明文 = `sha256(host_key)` 32 字节 ‖ 真实值（脚本用这 32 字节做自校验，
     对不上直接报错退出，不会把乱码当 cookie 交出去）。
   * `--save` 另存到 `~/.workbuddy/.secrets/`（0600）；不加参数只做只读预览。
   * 只支持 Chromium 系（Chrome / Edge / Brave / Arc），`--browser` 切换。

2. **非要用 F12**：先点 Sources 面板左上角 **Deactivate breakpoints**（⌘F8）把断点全关掉，
   `debugger` 就退化成空语句；再回 Network → 右键请求 → Copy as cURL。

**要不要配**：好价列表页**匿名可读**，线上实测匿名抓取数小时未被拦，所以默认留空即可。
配置登录态的收益不确定，代价是明确的：登录态来自你的家庭网络，而服务器走机房 IP，
站方可能提示异地登录，极端情况会把你自己的浏览器会话挤下线。**只在真的开始被拦时再配。**
